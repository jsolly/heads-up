# Durable, harness-independent delivery

The ship and sky producers run without AI on one persistent host. Each has a private `delivery.sqlite` next to its module. Replaceable webhook receivers own enrichment, rich chat replies and short texts. No OpenAI, xAI or email provider is built into the tracking core.

`HEADSUP_DESTINATIONS` is a comma-separated list of enabled lowercase names, at most eight. Each name requires injected `HEADSUP_<UPPERCASE_NAME>_URL` and `HEADSUP_<UPPERCASE_NAME>_KEY`. For example, the name `envoy` reads `HEADSUP_ENVOY_URL` and `HEADSUP_ENVOY_KEY`. Credentials belong in protected host configuration; never in tracked files or handoffs. When the list is absent, the existing `HEADSUP_WEBHOOK_URL`/`HEADSUP_WEBHOOK_KEY` form one `legacy` destination. An explicitly empty list disables all destinations. Publications with no configured receivers are recorded locally with no delivery jobs and are never backfilled later.

For the replacement rollout, enable only the approved relay destination. Keep xAI excluded. Removing a destination and running a delivery sweep or restarting its producer durably cancels pending attempts for that destination. Verify cancellation before re-enabling it. Adding a destination never backfills existing events. A request already in flight when a destination is disabled may complete; pausing a receiver is still a receiver-side responsibility.

A successful HTTP response means the receiver accepted the event. It does not prove chat or text completion. A receiving relay must commit the event and its channel jobs before returning success. Each channel needs a durable completion record keyed by event `id`; check `useful_until` and the current America/New_York 05:15–21:30 window before sending. HTTP retries are at least once: a crash after remote acceptance but before the local acknowledgement can repeat a POST. A channel crash after sending but before recording completion also needs provider idempotency or a supported reconciliation mechanism; exactly-once user notifications are not claimed here.

## Identity and crash recovery

Ship IDs contain a persistent transit UUID and event sequence; repeated ETA changes receive new sequences. An active pre-ledger transit receives a UUID on its next event. Watcher errors have independent UUIDs. `eta_at` provides a full local timestamp in addition to the display-only `eta_et`. `schema_version=1` applies to both event families.

The ship state atomically stores the emitted marker and complete publication intent together. On restart, intents are replayed before new AIS is consumed. SQLite publication atomically stores the immutable body and enabled destination snapshot. Clearing the source intent happens only after that commit. Crashes before publication retain an intent; crashes after publication repeat an idempotent insert. JSON replacement fsyncs its file and parent directory; SQLite uses FULL synchronous durability. This does not recover data from a reverted or lost host volume: backups outside that volume are a separate live gate.

Sky keeps its existing weather eligibility and retry state. Its body freezes at first ledger publication, including forecast time and useful lifetime; later forecast/geometry updates do not mutate a partly accepted event. Bad weather or expiry cancels remaining receiver jobs. A future opportunity gets a new occurrence ID. The immutable snapshot is a deliberate change from updating a network retry under the same ID.

`t60`, `t30`, `eta_shift` and `lost_signal` expire after 15 minutes, capped at the estimated pass time where available. `new_ship` expires after 30 minutes, also capped at pass time. `passed`, `stopped_short` and errors expire after 30 minutes. Sky expires at 75 minutes before sunrise/sunset or at celestial viewing time, capped at two hours after its forecast fetch. Quiet ship events stay local and are cancelled by transport; an in-window event can retry only while still useful. Receivers also enforce these gates on delayed delivery.

One asynchronous source worker per destination isolates stalled receivers, including across successive events. Network calls do not hold the publication/database lock. HTTP timeouts measure inactivity rather than a hard total deadline; the source sweep never joins a stalled destination, and response bodies are not consumed. Retries use exponential backoff capped at five minutes and reuse the first body and `Idempotency-Key`. Every destination acknowledgement commits separately. Terminal records remain for 30 days after expiry, then are removed during sweeps; SQLite reuses freed pages. Monitor private disk usage and source/receiver failures. Legacy `pending-events.jsonl` is historical evidence only and is not automatically replayed because it lacks reliable IDs and expiry.

## Host budget

Conservative initial budget: 1 vCPU, 2 GB RAM and 10 GB persistent disk, excluding map/image work. This is not a measured production minimum. The offline astronomy fixture suite on a Mac ARM laptop used about 55 MB peak RSS and 0.25 CPU seconds, with 0.35 seconds elapsed. Compact fixture ephemerides and short test windows do not measure the full production astronomy workload or total supervisor/ship/sky memory. AIS requires a continuous outbound TLS WebSocket; sky polls once per minute, retrieves forecasts hourly and computes astronomy roughly every six hours. Cache DE421 ephemeris and TLE data on disk. Allow outbound HTTPS to configured forecast, astronomy and receiver services. An intermittent Lambda invocation is not equivalent to the continuous AIS process.

The source uses ordinary Python and SQLite with no x86 assumption. Mac ARM tests do not prove Linux ARM packaging or host performance. Verify Python, NumPy, Skyfield, requests and websockets installation on the chosen architecture. Map rendering can stay assistant-side; the watcher host does not need Cartopy, Matplotlib, Shapely or PyProj. Full `requirements.txt` currently includes those map dependencies, so use the separated watcher requirements below for the persistent producer.

## AIS transport acceptance

The client negotiates permessage-deflate and requires both the handshake extension and AISStream CompressionEnabled confirmation before accepting stream coverage. It subscribes immediately after connection and resets coverage on every disconnect; confirmations and invalid/non-AIS messages do not refresh AIS health. Validate compression_enabled and live AIS timestamps after approved installation. AISStream has no durable replay or SLA, and its three-connection account/IP limits still apply. Compression avoids the documented uncompressed bandwidth penalty; it does not guarantee complete AIS coverage. Outbound IPv4 or a tested translation route is required when selected providers lack IPv6 reachability; verify DNS and connectivity on the chosen host. Source: https://aisstream.io/documentation .
